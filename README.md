# Software Engineering Standards

通用软件工程准则与最佳实践，涵盖工程原则、架构设计、代码质量、测试、Git 协作、数据安全、AI 辅助开发与交付流程。

## 项目简介

本仓库用于沉淀、整理和持续完善可跨项目复用的软件工程准则。

我们希望通过清晰、可执行的工程规则，为软件项目提供稳定的决策依据，提升代码质量、可维护性、安全性、可测试性与交付可靠性，同时避免过度设计和不必要的流程负担。

本仓库以个人实践、问题复盘和持续改进为基础，优先服务于不同软件项目的开发与维护，并为未来的公开分享和社区协作预留空间。

## 基本原则

- **通用性优先**：优先沉淀适用于不同项目和技术栈的工程原则。
- **实践导向**：规则应能够指导实际工作，并具备可判断、可验证的执行标准。
- **适度约束**：明确必要的质量底线，避免过度设计和形式主义。
- **依据明确**：区分已验证的事实、实践经验、推荐方案和待讨论的观点。
- **持续改进**：根据项目实践、问题复盘和技术发展持续修订规范。

## 规范主题

本仓库围绕以下八个主题逐步建设：

| 主题 | 主要内容 |
|---|---|
| 工程原则与架构决策 | 设计原则、架构权衡、复杂度控制与例外机制 |
| 代码组织与职责边界 | 模块划分、SOLID、Action、Service、领域逻辑与依赖管理 |
| 数据与安全 | 环境隔离、数据保护、权限控制与破坏性操作防护 |
| 测试与质量保证 | 测试策略、回归验证、质量门槛与自动化检查 |
| Git 与协作流程 | 分支、提交、代码评审、合并、发布与回滚 |
| 文档与项目状态管理 | 项目基线、技术决策、进度记录与交付文档 |
| 辅助开发 | 上下文核实、操作授权、变更控制与结果验证 |
| 交付与持续改进 | 验收、风险交接、复盘与规范迭代 |

以上为规划中的建设方向。各主题将经过逐项讨论与确认后形成正式规范，不预先视为已经采纳的规则。

## 规范状态

规范内容采用以下状态，以区分讨论意见与正式规则：

- **讨论中（Discussion）**：正在分析问题、比较方案或收集观点。
- **草案（Draft）**：已有初步规则文本，尚未正式采纳。
- **已采纳（Accepted）**：已确认，可作为项目实践的默认依据。
- **已废弃（Deprecated）**：不再推荐使用，保留历史记录及调整原因。

已采纳的通用规范仍需结合项目规模、技术栈、风险和实际约束合理应用。

## 如何使用本仓库

在启动或维护软件项目时，建议：

1. 明确项目目标、技术栈、风险和质量要求。
2. 选择适用的通用准则，作为项目工程实践的基础。
3. 根据具体技术栈和项目约束，补充必要的实现规范。
4. 对重要的架构和流程选择记录决策依据。
5. 通过测试、评审和实际运行结果验证规范的有效性。
6. 根据实践反馈改进项目规则，并评估是否需要更新通用准则。

通用准则提供默认指导，不意味着所有项目都必须采用完全相同的架构或流程。

## 通用规范与项目专属规则

本仓库遵循以下边界：

- **通用规范**：描述跨语言、跨框架的软件工程原则与实践。
- **技术栈指南**：描述特定语言、框架或工具中的推荐实现方式。
- **项目专属规则**：描述特定项目因业务、安全、部署或团队约束而增加的要求。

技术栈或项目专属规则不应在缺乏充分依据的情况下，直接推广为所有项目都必须遵守的通用规则。

## 参与与改进

规范建设遵循以下基本流程：

提出议题 → 分析问题与权衡 → 形成草案 → 确认并采纳 → 实践验证 → 持续改进。

讨论中的观点不会自动成为正式规范。重要规则的变更应尽可能说明变更动机、适用范围、预期收益、潜在成本及兼容性影响。

当前以个人维护和逐项讨论为主。未来开放社区协作时，将进一步明确贡献、评审与采纳流程。

## 语言约定

- 正文以中文为主，常见技术术语保留英文。
- 目录名、文件名和代码标识优先采用清晰、一致的英文命名。
- 规则应明确区分强制要求、默认做法与可选建议。

## 当前状态

本仓库处于初始建设阶段，八个主题正在逐项讨论。尚未完成讨论和确认的内容，不视为正式采纳的规范。

---

本仓库的目标不是追求规则数量，而是建立一套清晰、可执行、可验证，并能够随着项目实践持续改进的软件工程准则。
