# Software Engineering Standards

通用软件工程准则与最佳实践，涵盖工程原则、架构设计、代码质量、测试、Git 协作、数据安全、AI 辅助开发与交付流程。

## 项目简介

本仓库用于沉淀、整理和持续完善可跨项目复用的软件工程准则。

我们希望通过清晰、可执行的工程规则，为软件项目提供稳定的决策依据，提升代码质量、可维护性、安全性、可测试性与交付可靠性，同时避免过度设计和不必要的流程负担。

本仓库以个人实践、问题复盘和持续改进为基础，优先服务于不同软件项目的开发与维护，并为未来的公开分享和社区协作预留空间。

## 基本原则

- **通用性优先**：优先沉淀适用于不同项目和技术栈的工程原则。
- **实践导向**：规则应能够指导实际工作，并具备可判断、可验证的执行标准。
- **适度约束**：明确必要的质量底线，避免过度设计和形式主义。
- **依据明确**：区分已验证的事实、实践经验、推荐方案和待讨论的观点。
- **持续改进**：根据项目实践、问题复盘和技术发展持续修订规范。

## 规范状态

规范内容采用以下四种状态，以区分讨论意见、草案和正式规则：

- **讨论中（Discussion）**：正在分析问题、比较方案或收集观点，尚未形成相对稳定的规则文本。
- **草案（Draft）**：已有初步规则文本，仍需审查、讨论或修订，尚未正式采纳。
- **已采纳（Accepted）**：经维护者明确确认，可作为适用项目的默认工程依据。
- **已废弃（Deprecated）**：不再推荐使用，保留历史记录、调整原因及适用时的替代规范信息。

规范状态的管理遵循以下约定：

- 规范必须经过维护者明确确认，才能标记为 `Accepted`。
- 文件已创建、内容已补全、自动化检查已通过或变更已合并到主分支，都不代表规范已经正式采纳。
- 被新规则替代的旧内容继续使用 `Deprecated` 状态，并在适当位置说明替代关系；“已替代”是描述性说明，不是独立状态。
- 修改已采纳规范时，应根据变更影响决定是否重新讨论、评审或确认其状态。

已采纳的通用规范仍需结合项目规模、技术栈、风险和实际约束合理应用。涉及法律法规、合同义务或其他外部强制要求时，应遵循相应要求。

## 规范约束用语

为避免不同主题对规则强度产生不同理解，本仓库统一使用以下四类约束用语：

- **必须（MUST）**：适用条件成立时必须遵守的要求。
- **应当（SHOULD）**：默认应遵循的实践；偏离时应有合理理由，并考虑相关影响和风险。
- **建议（RECOMMENDED）**：值得优先考虑的实践，但不构成默认必须遵循的要求。
- **允许（MAY）**：明确许可的可选行为或方案，不代表该方案受到优先推荐，也不意味着项目必须采用。

阅读或应用具体规则时，应同时关注其适用范围、触发条件、上下文和约束强度，不应脱离实际情况机械套用。

四类术语的完整定义、例外处理方式及规范维护流程，以 [贡献与维护指南](CONTRIBUTING.md) 为准。各主题文档应遵循该指南中的统一定义，避免对相同术语作出不同解释。

## 如何使用本仓库

在启动或维护软件项目时，建议：

1. 明确项目目标、技术栈、风险和质量要求。
2. 选择适用的通用准则，作为项目工程实践的基础。
3. 根据具体技术栈和项目约束，补充必要的实现规范。
4. 对重要的架构和流程选择记录决策依据。
5. 通过测试、评审和实际运行结果验证规范的有效性。
6. 根据实践反馈改进项目规则，并评估是否需要更新通用准则。

通用准则提供默认指导，不意味着所有项目都必须采用完全相同的架构或流程。

## 通用规范与项目专属规则

本仓库遵循以下边界：

- **通用规范**：描述跨语言、跨框架的软件工程原则与实践。
- **技术栈指南**：描述特定语言、框架或工具中的推荐实现方式。
- **项目专属规则**：描述特定项目因业务、安全、部署或团队约束而增加的要求。

技术栈或项目专属规则不应在缺乏充分依据的情况下，直接推广为所有项目都必须遵守的通用规则。

## 参与与改进

规范建设遵循以下基本流程：

提出议题 → 分析问题与权衡 → 形成草案 → 评审与确认 → 正式采纳 → 实践验证 → 持续改进。

讨论中的观点不会自动成为正式规范。重要规则的变更应尽可能说明变更动机、适用范围、预期收益、潜在成本及兼容性影响。

当前以个人维护和逐项讨论为主。未来开放社区协作时，将进一步明确贡献、评审与采纳流程。

有关规范状态、约束用语、例外处理和贡献流程的具体约定，请参阅 [贡献与维护指南](CONTRIBUTING.md)。

## 语言约定

- 正文以中文为主，常见技术术语保留英文。
- 目录名、文件名和代码标识优先采用清晰、一致的英文命名。
- 规则应明确区分必须遵守的要求、默认应遵循的实践、优先推荐的实践与明确许可的可选行为。
- 各主题文档应使用统一的规范状态，并确保约束用语与本 README 及贡献指南保持一致。
