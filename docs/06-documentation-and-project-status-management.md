# 文档与项目状态管理

- **状态**：Draft
- **适用范围**：通用软件工程项目
- **主题定位**：规范项目文档、技术决策记录、任务状态管理及文档持续维护的基本要求

## 1. 目的与适用范围

本文建立通用的文档与项目状态管理准则，帮助项目沉淀必要的技术和业务知识，明确项目当前状态，降低协作中的信息不对称，并提高系统的可理解性和可维护性。

本文适用于个人维护、多人协作、开源项目以及具有持续开发和交付需求的软件项目。

本文不要求所有项目采用统一的文档目录、任务管理工具或决策记录模板。项目应根据业务复杂度、团队规模、维护周期、协作方式和风险等级选择合适的管理方式。

本文中的约束用语遵循 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 中的统一定义。
MUST、SHOULD、RECOMMENDED 和 MAY 的具体含义及例外处理原则以该指南为准；
本文不另行定义或改变其约束强度。

本文遵循以下原则：

- 文档应服务于实际使用、开发、维护和决策，而不是为了数量或形式而存在。
- 文档内容应准确、清晰，并与项目的实际行为保持一致。
- 项目状态应具有明确含义，避免任务进展和已知风险出现歧义。
- 重要技术决策应保留必要背景、理由和取舍，便于后续理解与复核。
- 文档应随相关变更及时更新，并持续处理过期或失效内容。
- 文档和状态管理的投入应与项目规模、复杂度和风险相匹配。

## 2. 文档建设原则

### 2.1 文档应解决实际问题

文档应帮助读者完成具体任务或理解重要信息，例如：

- 了解项目的目标、功能范围和主要限制。
- 安装、配置、运行和验证项目。
- 理解系统架构、模块职责及关键依赖。
- 了解重要业务规则、数据约束和安全要求。
- 排查常见问题并执行必要的维护操作。
- 理解重要技术决策及其适用条件。
- 了解当前任务进度、已知问题和后续计划。

不要求所有项目都编写上述全部类型的文档。应根据项目实际需求确定需要维护的内容。

### 2.2 文档投入应与复杂度匹配

文档的范围和详细程度应综合考虑：

- 项目功能与架构复杂度。
- 新成员或其他维护者的理解成本。
- 业务规则和技术决策的重要性。
- 部署、运行和故障处理的难度。
- 变更频率及文档失效的风险。
- 文档编写与长期维护的成本。

简单项目可以只维护 README 和少量必要说明。复杂系统则可能需要独立的架构文档、运维指南、决策记录和项目状态说明。

不应机械要求所有项目采用同样的文档体系，也不应以项目规模较小为理由，忽略必要的运行说明、安全要求或重要约束。

### 2.3 文档应保持准确且易于理解

文档应使用明确的术语、合理的结构和与实际任务相符的示例。

应避免：

- 无法解释实际行为的模糊描述。
- 与当前实现不一致的命令、配置或接口说明。
- 大量重复维护的相同内容。
- 缺乏上下文的缩写和内部术语。
- 没有明确用途且长期无人维护的文档。
- 将推测、计划或尚未验证的结论写成已确认事实。

必要时，应区分当前已实现的能力、计划中的功能、已知限制和待验证事项。

### 2.4 文档不应替代必要的验证

文档可以说明系统的预期行为和使用方式，但不能替代实际的测试、自动化检查或运行验证。

例如，文档中声明某项安全控制已经实现，并不代表该控制已经得到充分验证。

对于重要功能、接口、配置和操作流程，应根据风险通过测试、代码评审或其他适当方式确认其实际行为。

## 3. README 与文档组织

### 3.1 README 作为主要入口

README 应帮助读者快速理解项目，并找到进一步使用和维护项目所需的信息。

根据项目特点，README 可以包含：

- 项目定位、目标和主要能力。
- 适用范围及重要限制。
- 技术栈或主要依赖的简要介绍。
- 快速开始、安装或运行方式。
- 必要的配置说明。
- 测试和基本验证方式。
- 重要注意事项。
- 详细文档的导航入口。
- 项目当前状态或贡献方式。

不要求每个 README 都包含固定的全部章节。应优先提供读者最需要的信息，避免将 README 扩展成难以维护的完整技术手册。

### 3.2 按职责组织详细文档

当 README 无法清晰承载全部内容时，应根据文档的用途拆分组织。

例如：

- 使用与开发指南。
- 架构说明和模块边界。
- API 与数据结构说明。
- 部署、运维和故障处理指南。
- 技术决策记录。
- 项目计划、任务状态与已知问题。
- 贡献指南和工程规范。

目录结构应易于理解，并能够帮助读者快速找到相关内容。

不要求所有项目预先建立完整的多层目录。可以从少量必要文档开始，在信息规模和维护需求增长时逐步拆分。

### 3.3 避免重复维护相同信息

相同的规则或事实应尽量具有明确的主要维护位置。

其他文档可以通过链接、引用或简要概述指向主要来源，避免多个文件分别维护相互独立但内容相同的说明。

对于确实需要在不同场景中重复呈现的信息，应确保更新时不会产生相互矛盾的版本。

### 3.4 文档导航应保持有效

当项目具有多个文档时，应提供清晰的导航方式。

- 文档链接应指向正确位置。
- 文件或章节调整后，应更新相关引用。
- 对已废弃的文档，应明确其状态或提供迁移指引。
- 对仍然有效但用途不明显的文档，应补充必要的导航说明。

不要求所有项目都建立自动化链接检查，但对于文档规模较大或链接经常变动的项目，可以通过自动化工具降低维护成本。

## 4. 文档类型与维护边界

### 4.1 使用与开发文档

使用与开发文档应帮助读者理解如何使用项目、配置环境和开展开发工作。

根据项目特点，可以包括：

- 安装和运行步骤。
- 环境依赖与配置项说明。
- 本地开发和调试方法。
- 测试执行方式。
- 常见错误及处理方法。
- 开发环境与生产环境的必要区别。

命令和配置示例应尽可能可执行，并明确必要的前置条件。

对于依赖操作系统、运行时版本或外部服务的步骤，应说明重要限制，避免读者在不适用的环境中直接照搬。

### 4.2 架构与技术说明

架构文档应重点说明理解系统所需的关键结构和边界，例如：

- 系统主要模块及其职责。
- 重要的依赖关系和数据流。
- 外部系统与内部组件的交互。
- 关键业务规则和技术约束。
- 重要的可靠性、安全或扩展性考虑。

不要求将每个类、函数或内部实现都写入架构文档。

文档应侧重于帮助读者理解整体结构和重要设计意图。具体实现细节可以通过代码、类型定义、接口说明或其他适当方式表达。

### 4.3 API、配置与数据说明

当接口、配置项或数据结构具有明确的使用和维护需求时，应提供相应说明。

根据实际情况，内容可以包括：

- 接口用途、输入、输出和错误语义。
- 关键字段及其约束。
- 配置项的作用、默认行为和适用环境。
- 必要的权限、敏感性或安全限制。
- 兼容性、迁移和弃用要求。

对于能够从代码或工具可靠生成的内容，可以考虑自动生成或从单一来源维护，以减少重复劳动。

### 4.4 运维与故障处理文档

对需要持续运行或维护的系统，应根据风险记录必要的操作说明。

例如：

- 部署和升级步骤。
- 环境变量及配置要求。
- 健康检查和常见故障诊断。
- 备份、恢复和回滚方式。
- 关键日志、指标及告警说明。
- 需要人工执行的维护任务。

不要求所有项目都建立完整的运维手册。对于部署复杂、故障影响大或恢复成本高的系统，应优先记录那些能够降低事故风险和恢复时间的信息。

敏感凭证不得直接写入普通文档，应说明其安全获取和配置方式，而不是记录实际秘密值。

## 5. 技术决策与重要变更记录

### 5.1 识别需要记录的决策

并非所有实现细节都需要独立的技术决策记录。

当某项决策对架构、数据、安全、兼容性、长期维护成本或团队协作产生重要影响时，应考虑保留决策依据。

典型情况包括：

- 采用或更换重要的架构模式。
- 调整模块职责或关键依赖边界。
- 选择重要的数据库、存储方案或数据迁移方式。
- 改变认证、授权或敏感数据处理策略。
- 引入可能影响兼容性的接口或数据结构。
- 在多个具有明显取舍的技术方案之间做出选择。
- 确定重要的性能、可靠性或运维策略。

小范围实现调整和低影响的常规修改，可以通过 Commit、PR/MR 或简短说明追溯，无须强制建立正式决策文档。

### 5.2 记录决策的背景与理由

对重要决策，建议记录以下信息：

- **背景**：当前问题、业务目标或技术约束。
- **决策内容**：最终采用的方案及其适用范围。
- **考虑过的选项**：主要备选方案及关键差异。
- **决策理由**：为何选择当前方案。
- **取舍与风险**：已接受的成本、限制或潜在问题。
- **影响范围**：涉及的模块、接口、数据或维护流程。
- **决策状态**：例如讨论中、已采纳或已废弃；如被其他决策替代，应说明替代关系。

不要求每份决策记录都严格包含全部字段。记录深度应与决策的重要性相匹配，重点是让后续维护者理解为什么这样选择，而不只是知道最终结果。

本节中的决策状态属于项目决策管理，不等同于本仓库规范文件使用的 `Discussion`、`Draft`、`Accepted` 和 `Deprecated` 状态。对于已被替代的决策，应保留必要的历史记录并明确指向当前有效方案，不应将“已替代”作为本仓库规范状态体系之外的第五种状态。

### 5.3 使用适当的记录形式

项目可以根据自身规模选择合适的决策记录方式，例如：

- 设计文档中的决策章节。
- 独立的 Architecture Decision Record（ADR）。
- Issue 或 PR/MR 中的讨论记录。
- 与具体变更关联的维护说明。

对于存在多个长期有效架构决策的项目，可以采用统一的 ADR 目录或模板，方便查找和追踪。

不要求所有项目必须采用 ADR，也不要求每次技术选择都使用相同格式。

### 5.4 决策发生变化时保留必要历史

技术决策可能随着业务目标、依赖条件或系统规模变化而调整。

当重要决策被替代时，应根据需要更新其状态，并说明新的方案及变更原因。

不应仅通过覆盖旧内容来抹去仍有参考价值的历史背景。应让维护者能够理解原方案为什么曾经合理，以及后来为什么需要调整。

对于已经失效的方案，应明确标记，避免读者将历史记录误认为当前要求。

## 6. 项目状态与任务管理

### 6.1 状态应具有明确含义

项目应根据自身工作方式定义必要的任务状态，确保团队成员对进度和完成情况有一致理解。

例如，可以使用：

- **待处理**：已识别，但尚未开始。
- **进行中**：正在开展实际工作。
- **受阻**：因依赖、资源或其他原因无法继续。
- **待验证**：实现已完成，但仍需要必要的测试或确认。
- **已完成**：满足约定的完成条件。
- **已取消**：经确认不再需要继续处理。

以上状态仅为示例。项目可以采用更简单或更细致的状态体系，但应避免同一状态在不同场景下具有相互矛盾的含义。

### 6.2 明确任务范围与完成标准

任务记录应足以帮助执行者理解需要完成什么，以及如何判断工作已经完成。

对于重要任务，建议说明：

- 目标或待解决的问题。
- 主要工作范围。
- 预期结果或验收条件。
- 相关依赖和阻塞因素。
- 必要的测试、评审或文档要求。

简单任务可以使用简短标题和描述，不要求每个任务都填写完整模板。

### 6.3 根据需要记录责任人与阻塞因素

多人协作项目应根据工作方式明确重要任务的责任人或跟进方式。

对受阻任务，应尽量记录：

- 当前阻塞原因。
- 依赖的人员、任务或外部条件。
- 下一步需要采取的行动。
- 是否影响重要里程碑或交付计划。

不要求所有个人项目都设置正式责任人字段，但应避免重要工作长期处于无人跟进、状态不明的情况。

### 6.4 完成状态应反映实际结果

任务实现完成不一定意味着整个工作已经完成。

根据任务性质，完成条件可能还包括：

- 必要测试已通过。
- 代码评审或相关审批已完成。
- 配置和文档已更新。
- 数据迁移或兼容性验证已完成。
- 变更已部署，或已明确其交付状态。
- 已知风险和剩余工作已得到适当处理。

项目应根据实际工作定义完成标准，避免仅因为代码已编写就将任务标记为全部完成。

### 6.5 选择适合的任务管理工具

项目可以使用 GitHub Issues、项目看板、其他任务管理系统或轻量文档记录工作状态。

选择工具时，应考虑：

- 团队规模和协作方式。
- 任务数量与关联复杂度。
- 是否需要责任分配、提醒或统计。
- 是否需要与代码变更、发布或决策记录关联。
- 工具维护成本是否与实际收益相符。

不要求所有项目统一使用某一种工具。对于简单项目，清晰的 Markdown 清单可能已经足够；对于多人协作或依赖关系复杂的项目，则可以采用更系统的任务管理方式。

## 7. 计划、进度与已知问题

### 7.1 计划应区分目标与承诺

项目计划用于帮助团队理解工作方向、优先级和预期进展。

在记录计划时，应根据实际情况区分：

- 已确认的目标。
- 正在执行的工作。
- 尚未开始的计划。
- 存在不确定性的预期安排。
- 已明确的交付承诺。

不应将未经确认的估计或设想表达为确定承诺。

### 7.2 进度记录应反映实际情况

项目状态说明应及时反映重要进展、延迟和变化。

对于关键工作，可以记录已完成内容、当前进度、剩余工作和主要阻塞因素。

不要求所有项目定期编写固定格式的进度报告。记录频率应根据协作需要和项目风险决定，重点是让相关人员能够获得做出判断所需的信息。

### 7.3 已知问题应明确影响与处理状态

对于重要的已知问题，应根据需要记录：

- 问题表现和影响范围。
- 复现条件或相关环境。
- 当前处理状态。
- 已知的临时规避措施。
- 后续处理计划或优先级。
- 尚未解决的风险。

不要求记录所有微小问题，但不应隐瞒可能影响安全、数据完整性、可靠性或关键业务流程的问题。

## 8. 文档更新与过期内容治理

### 8.1 文档随相关变更同步更新

当变更影响文档所描述的实际行为时，应同步更新相关内容。

典型情况包括：

- 用户使用方式、安装或运行步骤发生变化。
- API、配置项或数据结构发生变化。
- 模块职责、架构边界或重要依赖发生变化。
- 安全要求、权限策略或重要约束发生变化。
- 部署、运维、备份或恢复流程发生变化。
- 项目状态、任务计划或技术决策发生重要变化。

不要求每次代码提交都更新所有文档。没有受到变更影响的文档，无须为了形式上的完整性进行无意义修改。

### 8.2 在变更流程中检查文档影响

项目可以在代码评审或变更检查清单中增加文档影响检查。

检查重点是：

- 现有说明是否仍然准确。
- 是否需要补充新功能或新限制的使用说明。
- 是否需要调整相关示例、配置或命令。
- 是否需要更新架构、决策或运维记录。
- 是否存在已失效的链接或互相矛盾的描述。

对于影响范围明确的小修改，可以只检查直接相关的文档；对于重要架构或交付变更，应评估更广泛的文档影响。

### 8.3 及时识别和处理过期文档

发现文档过期、失效或与实际行为不一致时，应根据影响程度及时修正。

可以采用以下方式：

- 更新已经变化的内容。
- 将历史资料明确标记为归档或已废弃。
- 删除没有保留价值且容易误导读者的内容。
- 将重复内容合并到主要维护位置。
- 修复失效链接和错误示例。
- 对尚未验证的内容明确标注状态和限制。

对于无法立即修复的非关键文档问题，可以记录后续处理事项；对于可能导致错误操作、安全风险或严重故障的问题，应优先处理。

### 8.4 避免无效的文档维护流程

文档维护应关注内容的准确性和使用价值，而不是单纯追求文件数量、更新频率或形式上的完整。

不应要求每次无关代码变更都修改 README，也不应通过机械增加更新时间、版本号或重复声明来替代内容审查。

对于能够自动生成且来源可靠的文档，可以使用自动化方式减少重复维护，但仍应确保生成结果准确、可访问并符合实际使用需求。

## 9. 文档与项目状态的可信度

### 9.1 区分事实、计划与待确认事项

项目文档应明确表达信息的确定程度。

对于重要信息，应根据需要区分：

- 已实现并经过验证的能力。
- 已确认但尚未完成的工作。
- 仍在讨论中的方案。
- 尚未验证的假设。
- 已知限制或暂时无法解决的问题。

不应将计划中的功能描述为已经可用，也不应将未经验证的结论表达为确定事实。

### 9.2 保持状态来源清晰

同一任务或决策如果在多个地方出现，应尽量明确主要维护位置。

其他文档可以引用主要来源，但应避免出现多个互不一致的状态副本。

对于重要工作，应让维护者能够找到当前状态、相关讨论和必要的历史记录。

### 9.3 变更历史应与当前状态互补

Commit、PR/MR、Issue 和决策文档可以共同提供项目历史信息，但它们不能完全替代当前状态说明。

版本历史适合追溯发生过什么；当前文档应帮助读者理解现在应该如何使用、维护或继续开发项目。

项目应根据需要同时维护当前有效的说明和必要的历史记录，避免要求读者通过大量历史提交才能还原基本使用方式。

## 10. 文档与状态管理检查清单

以下清单可用于项目建设、代码评审、重要变更和日常维护。应根据项目规模和风险选择适用项。

### 文档结构与内容

- [ ] README 能够说明项目定位、基本使用方式和主要文档入口。
- [ ] 详细文档按照实际用途组织，结构清晰。
- [ ] 关键使用、配置、接口或运维信息已得到适当说明。
- [ ] 重要文档与当前实现保持一致。
- [ ] 相同信息具有明确的主要维护位置。
- [ ] 重要文档链接和示例没有明显失效。

### 技术决策与历史

- [ ] 重要架构、数据、安全或兼容性决策具有必要的记录。
- [ ] 重要决策的背景、理由和关键取舍能够被理解。
- [ ] 已被替代或废弃的决策具有明确状态。
- [ ] 重要变更能够通过 Commit、PR/MR 或其他记录追溯。

### 项目状态与任务

- [ ] 重要任务具有明确的目标和完成条件。
- [ ] 任务状态能够反映实际进度。
- [ ] 重要阻塞因素、依赖和责任分配已经明确。
- [ ] 计划、已完成工作和待确认事项能够区分。
- [ ] 重要已知问题及其风险具有适当记录。

### 文档维护

- [ ] 变更影响使用、接口、配置、架构或运维流程时，已检查相关文档。
- [ ] 过期、矛盾或失效的内容已得到处理或明确标记。
- [ ] 文档更新与代码变更的实际范围一致。
- [ ] 未验证的能力、计划事项和已知限制没有被误写为确定事实。

清单用于辅助判断，不要求所有项目在每次修改时执行全部检查。应根据变更影响、信息重要性和维护成本确定检查范围。

## 11. 与其他规范的关系

本文规定项目文档、技术决策记录、任务状态和文档维护方面的通用要求。

- **工程原则与架构决策**：定义工程质量底线、设计权衡和架构决策方式。
- **代码组织与职责边界**：明确代码组织、模块职责和依赖边界。
- **数据与安全**：定义数据完整性、身份认证、访问授权和敏感信息保护要求。
- **测试与质量保证**：规范测试策略、质量检查、回归测试和持续集成。
- **Git 与协作流程**：规范分支、提交信息、代码评审、合并和变更追溯。
- **AI 辅助开发**：规范 AI 生成内容的审查、验证及相关风险控制。
- **交付与持续改进**：规范发布、部署、运行反馈、故障复盘和持续改进。

本文不要求所有项目采用统一的文档结构、任务管理工具或决策记录模板。项目应在保证重要信息准确、关键状态清晰和必要决策可追溯的前提下，选择适合自身维护方式的管理机制。
