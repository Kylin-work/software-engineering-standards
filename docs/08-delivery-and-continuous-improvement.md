# 交付与持续改进

- **状态**：Draft
- **适用范围**：通用软件工程项目
- **主题定位**：规范软件交付、发布部署、故障恢复、运行监控和持续改进的基本要求

## 1. 目的与适用范围

本文建立通用的软件交付与持续改进准则，帮助项目以可验证、可控和可恢复的方式交付软件，并通过运行反馈持续提升质量、可靠性和维护效率。

本文适用于个人项目、团队协作项目、开源软件、内部系统、在线服务及其他具有交付或持续维护需求的软件项目。

本文不要求所有项目采用统一的发布工具、部署架构、监控平台或审批流程。项目应根据业务影响、技术复杂度、交付频率、故障风险和恢复成本选择适当的工程措施。

本文中的约束用语遵循 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 中的统一定义。
MUST、SHOULD、RECOMMENDED 和 MAY 的具体含义及例外处理原则以该指南为准；
本文不另行定义或改变其约束强度。

本文遵循以下原则：

- **交付可验证**：交付物应满足明确的质量要求和必要的验收条件。
- **发布可控**：发布范围、执行方式和风险应得到适当管理。
- **过程可重复**：优先使用一致、可复现且易于检查的交付流程。
- **失败可恢复**：提前评估故障影响，并准备适当的回滚、修复或恢复方案。
- **运行可观察**：根据系统重要性获取足够的运行信息，以便发现和处理问题。
- **改进有闭环**：将缺陷、故障和交付经验转化为可执行的改进措施。
- **投入与风险匹配**：避免忽略必要的质量控制，也避免引入与项目规模不相称的流程负担。

## 2. 交付标准与质量门禁

### 2.1 明确交付条件

交付前应根据变更类型和影响范围，明确需要满足的条件。

适用的交付条件可以包括：

- 已完成约定的功能和需求。
- 必要的代码评审已完成。
- 相关测试和质量检查已通过。
- 配置、依赖和环境要求已确认。
- 重要的安全风险已得到处理或明确接受。
- 必要的文档和操作说明已更新。
- 已知缺陷、限制和剩余风险已得到记录。
- 发布、部署及恢复方式已经明确。

不要求所有项目的每次变更都满足完全相同的检查清单。应根据变更的风险和实际影响确定适用的交付门槛。

### 2.2 根据风险设置质量门禁

质量门禁用于阻止尚未满足必要要求的变更进入后续交付阶段。

项目可以根据需要设置以下检查：

- 代码格式与静态分析。
- 类型检查和构建验证。
- 单元测试、集成测试及回归测试。
- 依赖和安全漏洞检查。
- API 或数据结构兼容性检查。
- 代码评审与必要的人工审批。
- 部署前检查及发布后验证。

对于涉及安全、关键业务逻辑、数据完整性或高影响生产系统的变更，应设置更严格的检查和审批要求。

对于低风险的小型项目，可以采用较轻量的流程，但不应省略防止重大缺陷、安全问题或不可恢复损失所必需的控制。

### 2.3 明确质量门禁的例外处理

如果某项检查暂时无法通过或不适用于当前变更，应明确其原因及影响，而不是默认绕过。

对于可以接受的例外，应根据风险确定：

- 例外的具体范围。
- 允许例外的理由。
- 潜在影响与补偿措施，以及必要的有效性验证方式。
- 补偿措施实施后仍然存在的剩余风险及其责任承担方。
- 必要的审批责任人。
- 后续处理计划和期限。
- 必要的复评条件。

涉及重大安全、数据完整性或业务风险的问题，不得仅为了满足交付时间而无条件放行。此类例外必须经过适当的责任方评估和确认，并明确补偿控制、剩余风险、处理期限及复评条件。法律法规、合同义务及其他不可豁免的约束，不得通过项目内部例外机制绕过。

### 2.4 区分开发完成、交付完成与部署完成

代码开发完成不一定意味着软件已经完成交付，也不代表软件已经部署并正常运行。

项目应根据实际交付范围区分：

- **开发完成**：约定的实现工作已完成。
- **交付准备完成**：必要的验证、制品准备、配置确认和交接工作已完成。
- **部署完成**：变更已应用到目标环境。
- **运行验证完成**：必要的发布后检查已通过，结果符合预期。

以上是用于明确工作含义的示例，不要求所有项目都采用固定的四阶段状态体系。项目应选择能够准确表达自身流程的状态。

不得将尚未执行的测试、未完成的部署或未经验证的运行结果描述为已经完成。

## 3. 构建与交付物管理

### 3.1 尽可能保证构建可重复

在条件允许时，应使构建过程具有一致性和可重复性。

应根据项目特点明确：

- 运行时和构建工具的必要版本。
- 依赖管理和版本锁定策略。
- 构建所需的环境配置。
- 构建命令和必要参数。
- 构建产物的输出位置与验证方式。

对于依赖较多、运行环境复杂或交付频率较高的项目，应优先减少构建对个人环境和未记录状态的隐式依赖。

不要求所有项目都实现完全可复现构建，但应尽量让构建过程稳定、可理解，并能够在出现问题时进行排查。

### 3.2 明确交付物的身份与来源

对于需要持续部署或正式发布的软件，应根据需要明确交付物的版本、来源和构建记录。

例如：

- 版本号或其他唯一标识。
- 对应的源代码提交。
- 构建时间和构建环境。
- 重要依赖及其版本。
- 必要的校验值或签名信息。

具体记录要求应与项目的供应链风险、审计需求和交付方式相匹配。

对于安全敏感或影响范围较大的项目，应考虑通过制品签名、来源验证或其他适当措施，提高交付物的完整性和可信度。

### 3.3 区分构建、测试与生产环境

项目应根据需要明确不同环境的用途及其配置边界。

应避免：

- 将生产凭证直接用于本地开发或测试。
- 将未经验证的开发制品直接用于生产。
- 依赖未记录的个人环境配置完成正式发布。
- 因环境差异导致重要行为无法复现。
- 在测试环境中使用未经授权的生产数据。

环境隔离的具体程度应根据数据敏感性、业务影响和运行风险确定。

### 3.4 管理配置与秘密信息

交付和部署所需的配置应具有清晰的来源、作用和维护方式。

应区分普通配置与凭证、密钥等敏感信息。

敏感信息应通过适当的秘密管理机制提供，不应直接写入源代码、普通配置文件、构建日志或公开文档。

对重要配置变更，应根据需要执行审查、验证和版本记录，避免因配置漂移导致难以定位的运行问题。

## 4. 部署与发布策略

### 4.1 选择适合的发布方式

发布策略应根据系统架构、用户规模、故障影响和恢复能力确定。

可选方式包括：

- **直接发布**：适合影响范围有限、容易验证和恢复的项目。
- **分批发布**：将变更逐步应用到不同实例或用户范围。
- **灰度发布**：先向有限流量或指定用户开放变更，再逐步扩大范围。
- **蓝绿部署**：准备两个可切换的运行环境，以降低切换过程中的风险。
- **功能开关**：通过配置控制功能的启用范围或启用时间。

这些方式各有成本和适用条件，不要求所有项目都实现复杂的发布策略。

应优先选择与实际风险相匹配、团队能够可靠维护的方式。

### 4.2 优先使用可重复的自动化流程

对于重复执行的构建、测试、打包和部署任务，应评估自动化的价值。

自动化可以减少手工操作差异，提高执行一致性，并使关键步骤更容易检查和追溯。

自动化流程应根据需要明确：

- 执行顺序和依赖关系。
- 必要的权限与环境变量。
- 失败时的停止条件。
- 重要步骤的检查与审批要求。
- 执行结果的记录方式。
- 失败后的恢复或重试策略。

自动化并不意味着无条件自动放行。对于高风险操作，应保留必要的审批、保护规则和执行边界。

### 4.3 根据风险决定发布频率与粒度

小而明确的变更通常更容易审查、验证和定位问题。

在不违背业务约束的前提下，应避免将大量无关变更集中到一次难以审查或恢复的发布中。

发布频率应综合考虑：

- 业务交付需求。
- 自动化验证的成熟度。
- 系统稳定性和故障影响。
- 变更之间的依赖关系。
- 发布与恢复的实际成本。

不要求所有项目追求高频发布。对低频交付、离线软件或具有严格审批要求的系统，应采用符合其业务和合规条件的发布节奏。

### 4.4 明确发布前的准备事项

对于重要发布，应根据风险确认：

- 发布内容和目标版本。
- 相关测试与质量检查结果。
- 配置、权限和环境准备情况。
- 数据库或数据迁移要求。
- 兼容性和依赖影响。
- 发布窗口及必要的协作安排。
- 发布后的验证方式。
- 失败时的回滚或前向修复方案。
- 必要的通知、审批和责任分工。

对于简单项目，可以通过简短的检查清单完成准备；对于高影响系统，应建立更完整的发布管理机制。

### 4.5 发布后确认实际结果

发布完成不代表变更已经被证明正常。

对于具有运行环境的系统，应根据变更风险确认：

- 应用或服务能够正常启动。
- 关键健康检查通过。
- 核心功能和必要接口可正常工作。
- 错误率、延迟或其他重要指标没有出现异常。
- 数据处理和外部依赖符合预期。
- 发布版本与预期版本一致。

如果发布后出现异常，应根据预先确定的响应机制判断是否停止继续发布、回滚或进行前向修复。

对于无法自动确认运行状态的交付物，应明确适用的人工验收或验证方式，不应将无法观察误认为运行正常。

## 5. 失败处理与回滚

### 5.1 发布前评估失败风险

对于可能影响重要业务、数据或生产环境的变更，应在发布前识别主要失败模式。

应根据需要评估：

- 哪些条件表明发布失败。
- 失败会影响哪些用户、服务或数据。
- 如何发现问题并判断影响范围。
- 如何停止继续扩大影响。
- 是否能够回滚到之前的版本或状态。
- 是否需要前向修复、数据恢复或人工介入。
- 恢复过程可能造成的额外风险。
- 如何验证恢复是否成功。

不要求所有小型项目都编写正式的风险分析报告，但不能在高风险变更中完全忽略失败处理方式。

### 5.2 区分回滚与前向修复

回滚是恢复到先前版本或状态；前向修复则是在当前状态上实施修正，以恢复预期行为。

并非所有问题都适合回滚。

选择处理方式时，应考虑：

- 当前系统状态是否兼容旧版本。
- 数据是否已经发生不可逆变化。
- 是否存在外部系统或用户已经观察到的副作用。
- 回滚是否会重新引入已修复的缺陷。
- 前向修复能否更安全地恢复服务。
- 是否需要配合数据修复或人工处理。

应选择风险更可控、能够满足恢复目标的方案，而不是机械要求所有发布都必须一键回滚。

### 5.3 特别考虑数据库与数据迁移

数据变更可能使软件版本之间不再兼容，因此数据迁移需要单独评估。

对于重要迁移，应根据需要考虑：

- 迁移前的备份或其他恢复保障。
- 新旧应用版本的兼容关系。
- 迁移步骤是否可重复执行。
- 部分成功时的状态和恢复方法。
- 是否存在不可逆的数据转换。
- 迁移过程对读写和服务可用性的影响。
- 恢复时是否需要额外的数据修复。

采用扩展后收缩（Expand and Contract）等兼容性策略，可以在适当场景下降低应用与数据结构切换时的风险。

对于不可逆或无法简单回滚的数据操作，应提前明确替代恢复方案、风险承担责任及必要的审批。备份存在不等于恢复能力已得到验证；对重要数据，应根据风险验证备份的可用性和恢复流程。

### 5.4 明确停止条件与升级路径

当发布或部署过程中出现重要异常时，应根据预先确定的条件停止继续扩大变更影响。

应明确何时需要：

- 暂停发布或停止后续批次。
- 关闭相关功能开关。
- 执行回滚或前向修复。
- 通知相关责任人。
- 升级为正式故障事件。
- 暂停自动化流程并转入人工处理。

对于自动化部署，应避免在缺乏有效判断的情况下持续重试可能造成额外损害的操作。

### 5.5 验证恢复结果

执行回滚或修复后，应确认系统确实恢复到预期状态。

根据故障性质，应检查：

- 核心功能是否恢复。
- 错误率和关键指标是否回到可接受范围。
- 数据状态是否正确。
- 外部依赖和任务处理是否正常。
- 是否仍存在未解决的副作用。
- 后续发布是否需要额外限制。

仅完成回滚命令或修复提交，并不能自动证明服务和数据已经恢复。

## 6. 运行监控与可观测性

### 6.1 根据系统重要性建立适当的监控

运行中的系统应具备与其重要性相匹配的状态观察和问题发现能力。

根据项目特点，可以采用：

- **日志（Logs）**：记录关键事件、错误和必要上下文。
- **指标（Metrics）**：观察请求量、错误率、延迟、资源使用和业务状态。
- **链路追踪（Traces）**：分析跨服务请求的执行路径和延迟来源。
- **健康检查（Health Checks）**：确认应用及必要依赖是否处于可接受状态。
- **告警（Alerts）**：在重要异常发生时通知相关人员。

不要求所有项目都部署完整的可观测性平台。简单项目可以从清晰的错误日志和基本健康检查开始，逐步增加能够实际改善问题发现与诊断效率的能力。

### 6.2 监控应服务于实际问题

监控指标和日志应能够帮助回答重要问题，例如：

- 系统是否正常提供核心功能。
- 用户是否受到明显影响。
- 错误是否持续增加。
- 延迟和资源使用是否异常。
- 外部依赖是否发生故障。
- 最近的变更是否可能与异常有关。

不应仅为了收集数据而无限增加指标、日志或告警。

监控内容应有明确用途，并根据实际排障经验持续调整。

### 6.3 建立有行动意义的告警

告警应优先关注需要及时处理的实际风险。

应尽量明确：

- 触发条件及其含义。
- 影响的系统或业务范围。
- 严重程度和处理优先级。
- 相关诊断信息。
- 负责响应的人员或机制。
- 必要的处理指南和升级路径。

应定期处理重复、误报或没有明确行动价值的告警，避免告警疲劳降低真正重要通知的有效性。

### 6.4 保护日志与监控数据

日志、指标、追踪数据和告警信息可能包含敏感内容。

应根据需要控制：

- 凭证、密钥和个人信息的记录。
- 生产数据及业务标识符的暴露。
- 日志和监控系统的访问权限。
- 数据保存期限和删除方式。
- 外部监控服务的数据传输范围。

不应为了方便排查问题而无条件记录所有请求内容或敏感字段。

### 6.5 根据实际能力设置服务目标

对于持续运行且具有明确可用性要求的服务，可以根据业务需求定义服务级别目标（Service Level Objective，SLO）或其他运行目标。

例如：

- 服务可用性。
- 请求成功率。
- 响应延迟。
- 任务处理完成时间。
- 数据处理正确性。
- 故障恢复时间。

不要求所有项目都制定正式的 SLO 或服务级别协议（Service Level Agreement，SLA）。对于重要服务，应确保运行目标与用户需求、业务影响和实际恢复能力相匹配。

## 7. 故障响应与沟通

### 7.1 根据影响确定故障响应等级

项目应根据故障影响决定响应方式。

需要考虑的因素包括：

- 影响用户的范围和数量。
- 核心业务是否中断。
- 数据完整性或安全性是否受到影响。
- 是否存在持续扩大的风险。
- 是否有可用的临时规避措施。
- 恢复服务所需的时间和资源。

高影响故障应优先控制损害并恢复关键功能。低影响问题则可以根据优先级进入正常缺陷处理流程。

### 7.2 响应过程中优先控制影响

发生重要故障时，应优先：

1. 确认当前已知事实和影响范围。
2. 阻止故障继续扩大。
3. 恢复关键服务或提供适当的临时措施。
4. 保留必要的日志、指标和诊断信息。
5. 向相关人员传达已知情况和处理进度。
6. 在服务稳定后继续分析根因和改进措施。

不应在缺乏足够证据时过早确定根因，也不应因追求完整分析而延误必要的止损和恢复行动。

### 7.3 明确必要的沟通机制

对于多人协作或影响用户的系统，应根据需要明确故障期间的信息传递方式。

沟通内容可以包括：

- 已确认的故障表现。
- 当前影响范围。
- 已采取的措施。
- 尚未确认的信息。
- 下一步计划。
- 用户需要采取的行动。

应区分已确认事实、初步判断和待验证假设，避免将推测作为确定结论传播。

### 7.4 记录重要故障及恢复过程

对于影响较大、反复发生或暴露系统性问题的故障，应保留必要的事件记录。

记录可以包括：

- 发生时间和发现方式。
- 影响范围与持续时间。
- 关键事件时间线。
- 主要处理措施。
- 恢复过程与验证结果。
- 已知根因或待确认问题。
- 后续改进事项。

不要求所有小型缺陷都形成正式的故障报告，但重要事件应保留足以支持后续分析的信息。

## 8. 持续改进与复盘

### 8.1 将运行反馈转化为改进机会

持续改进的输入可以来自：

- 生产故障与服务中断。
- 用户反馈和支持请求。
- 测试失败与质量问题。
- 发布和部署过程中的异常。
- 安全检查与风险评估。
- 代码评审和维护过程中的重复问题。
- 性能、成本和资源使用趋势。
- 工程流程中的等待、返工和协作障碍。

项目应根据影响和优先级处理这些信息，不要求所有反馈都立即转化为正式任务。

### 8.2 根据影响开展适度复盘

对于重大故障、重复性问题或影响重要工程目标的事件，应开展适当复盘。

复盘的重点是理解：

- 实际发生了什么。
- 哪些预期与实际情况不一致。
- 哪些技术、流程或组织条件促成了问题。
- 哪些控制措施未能发挥预期作用。
- 哪些措施能够降低再次发生的概率或影响。

复盘应以事实和证据为基础，关注系统性原因、工程机制和改进机会，而不是简单归咎于某个人。

不要求每个小缺陷或每次发布都进行正式复盘。复盘的深度应与事件影响、重复频率和潜在风险相匹配。

### 8.3 区分直接原因与系统性原因

直接原因可以解释故障是如何发生的，但未必能够说明为什么现有工程机制未能预防或及时发现问题。

复盘时应根据情况检查：

- 需求或设计中的遗漏。
- 代码和数据约束中的缺陷。
- 测试覆盖或质量门禁不足。
- 配置、部署或环境差异。
- 监控与告警不充分。
- 权限、流程或责任边界不清晰。
- 过于复杂或难以恢复的系统设计。

不应仅通过要求个人更加谨慎来替代必要的系统改进。

### 8.4 改进措施应可执行且可验证

复盘结果应根据重要性转化为明确的改进事项。

对于重要行动项，建议记录：

- 需要解决的问题。
- 预期达到的目标。
- 具体执行措施。
- 责任人或跟进方式。
- 优先级与必要期限。
- 如何判断措施已经完成并产生效果。

改进措施可以包括修复缺陷、补充测试、改善监控、调整部署流程、更新文档或改变架构设计。

不应只记录“加强测试”“提高警惕”等无法直接执行和验证的笼统要求。

### 8.5 跟踪改进结果

改进任务完成后，应根据需要确认其是否解决了目标问题。

例如：

- 原有故障是否能够通过新增测试发现。
- 告警是否能更早发现相关异常。
- 部署失败是否更容易恢复。
- 重复性人工操作是否已得到简化。
- 相关文档是否降低了使用或维护错误。
- 同类问题是否再次出现。

对于效果不明显的措施，应重新评估原因并调整方案。

持续改进不以任务数量或文档数量作为唯一衡量标准，而应关注实际风险是否降低、质量是否改善、交付是否更可靠。

## 9. 交付效率与工程成本

### 9.1 兼顾交付速度与长期维护成本

提高交付速度不应以显著增加故障风险、维护负担或未来返工为代价。

项目应综合考虑：

- 交付周期和反馈速度。
- 缺陷率与返工成本。
- 发布失败和恢复成本。
- 自动化建设与维护成本。
- 系统复杂度及团队认知负担。
- 运行资源与基础设施成本。

应优先改善造成明显等待、重复劳动或高风险操作的环节，而不是为了追求流程自动化而增加不必要的系统复杂度。

### 9.2 自动化应具有明确收益

对于重复、稳定且容易定义验证条件的任务，可以优先考虑自动化。

适合评估自动化的环节包括：

- 构建与测试。
- 代码质量和依赖检查。
- 制品生成与发布准备。
- 部署和健康检查。
- 日常维护与状态报告。

自动化本身也需要维护。对于低频、低风险或规则尚未稳定的任务，可以先使用清晰的人工流程，再根据实际收益决定是否自动化。

### 9.3 逐步改善工程流程

持续改进可以从小范围、可验证的调整开始。

例如：

- 减少重复的人工部署步骤。
- 将容易遗漏的检查加入自动化流程。
- 改善错误日志和诊断信息。
- 降低测试执行时间。
- 明确发布失败后的处理方式。
- 统一重复使用的操作指南。
- 减少反复出现的协作阻塞。

每项改进都应有明确的问题背景和预期效果。对于影响较大的流程调整，应在实施后检查实际结果，并根据反馈继续优化。

## 10. 交付与持续改进检查清单

以下清单可用于发布准备、部署检查、故障处理和工程改进。应根据项目规模、变更影响和运行风险选择适用项。

### 发布准备

- [ ] 本次交付范围、版本和验收条件明确。
- [ ] 必要的测试、评审和质量门禁已完成。
- [ ] 配置、依赖和环境要求已确认。
- [ ] 重要安全风险、兼容性问题和已知限制已得到处理或记录。
- [ ] 必要的发布说明和操作文档已更新。
- [ ] 失败处理方式和必要的审批要求明确。

### 构建与部署

- [ ] 构建过程及交付物来源能够按需追溯。
- [ ] 部署流程可重复，并具有必要的执行检查。
- [ ] 发布方式与变更风险相匹配。
- [ ] 高风险操作具有适当的权限控制和确认机制。
- [ ] 发布后验证方式明确。

### 恢复与运行

- [ ] 重要故障的发现条件和停止条件明确。
- [ ] 已评估回滚、前向修复或其他恢复方式。
- [ ] 数据变更的兼容性和恢复限制已得到考虑。
- [ ] 重要服务具有适当的日志、指标或健康检查。
- [ ] 告警具有明确的处理方式和责任归属。
- [ ] 恢复后已验证服务与数据状态。

### 持续改进

- [ ] 重要故障和重复性问题得到适当记录。
- [ ] 复盘关注事实、根因和系统性改进。
- [ ] 改进事项具有明确目标和可执行措施。
- [ ] 重要行动项具有适当的责任分配和跟踪方式。
- [ ] 已根据需要检查改进措施的实际效果。

该清单用于辅助判断，不要求所有项目在每次变更时执行全部检查。应根据业务影响、技术风险和维护成本确定适用范围。

## 11. 与其他规范的关系

本文规定软件交付、发布部署、故障恢复、运行监控和持续改进方面的通用要求。

- **工程原则与架构决策**：为交付可靠性、系统复杂度和长期维护提供设计依据。
- **代码组织与职责边界**：明确实现边界，降低变更、测试和部署的复杂度。
- **数据与安全**：规范数据完整性、访问控制、敏感信息保护和安全风险处理。
- **测试与质量保证**：为发布前验证、回归测试和质量门禁提供基础。
- **Git 与协作流程**：支持变更审查、版本追溯、发布记录和协作责任划分。
- **文档与项目状态管理**：维护交付说明、运行指南、已知问题和项目进度。
- **AI 辅助开发**：规范 AI 参与交付准备、故障分析和工程改进时的审查与验证要求。

本文不要求所有项目采用统一的交付平台、监控系统或复盘制度。项目应在保证必要质量、可控发布和可恢复性的前提下，建立与自身风险和能力相匹配的交付机制，并持续依据实际反馈进行改进。
