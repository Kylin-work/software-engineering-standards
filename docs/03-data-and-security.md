# 数据与安全

- **状态**：Draft
- **适用范围**：通用软件工程项目
- **主题定位**：规范数据管理、身份认证、访问授权、敏感信息保护、数据一致性与安全风险控制

## 1. 目的与适用范围

本文建立通用的数据管理与安全准则，帮助项目保护数据的机密性、完整性和可用性，降低未授权访问、数据泄露、数据损坏及业务状态不一致等风险。

本文适用于数据建模、数据存储、数据访问、接口交互、身份认证、访问授权、敏感信息处理、事务管理及外部系统集成等场景。

本文遵循以下原则：

- 明确数据的业务含义、所有权和访问边界。
- 将必要的安全控制作为质量底线，而不是可选优化项。
- 根据业务不变量、威胁和失败风险选择适当的技术措施。
- 优先使用成熟、经过验证的安全机制，避免重复实现容易出错的基础能力。
- 在满足安全和数据完整性要求的前提下，控制实现复杂度与运维成本。

本文不强制特定数据库、领域建模方法、身份认证协议或安全产品。项目应根据业务类型、数据敏感程度、系统暴露范围、监管要求及运行环境确定具体实施方式。

本文中的 MUST、SHOULD、RECOMMENDED 和 MAY 遵循 `CONTRIBUTING.md` 中的统一约束用语定义，不在本文件中另行定义或改变其约束强度。

## 2. 基本原则

### 2.1 明确数据所有权与访问边界

每类重要业务数据都应有明确的业务归属和维护责任。

- 明确哪些模块或服务负责创建、读取、修改和删除数据。
- 避免多个模块在缺乏约定的情况下随意修改同一业务状态。
- 对共享数据，应明确其访问方式、修改权限和一致性要求。
- 跨模块或跨服务访问数据时，应优先使用明确的接口或约定，而不是随意依赖其他模块的内部实现。

数据所有权不意味着每个项目都必须采用微服务或独立数据库。对于单体应用，可以通过模块职责、数据访问组件和权限约定实现清晰的边界。

### 2.2 保护机密性、完整性与可用性

数据保护应综合考虑：

- **机密性**：避免数据被未授权人员或系统访问。
- **完整性**：避免数据被未授权或不符合业务规则地修改。
- **可用性**：确保授权业务在合理的故障范围内能够使用所需数据。

不同数据和操作的风险并不相同。项目应根据数据敏感程度、业务影响及恢复要求确定相应控制措施。

### 2.3 默认安全与最小权限

系统应默认采用安全配置，并只授予完成必要工作所需的权限。

- 新增访问能力时，应明确其授权依据。
- 未明确允许的访问不应被默认视为合法。
- 服务账号、数据库账号和第三方凭证应遵循最小权限原则。
- 不应因为实现方便而授予不必要的管理员权限或扩大数据访问范围。

### 2.4 将安全要求纳入设计与开发

安全不应只在上线前或发生事故后才考虑。

设计阶段应识别重要数据、信任边界和主要威胁；开发阶段应实施必要的输入验证、访问控制和错误处理；测试与交付阶段应验证关键控制是否有效。

安全措施的深度应与风险相匹配，但不得以降低实现成本为由省略必要的安全底线。

## 3. 数据建模与完整性约束

### 3.1 根据业务含义建模

数据模型应反映业务含义、状态和约束，而不是只追求数据库表结构简单或通用。

- 明确重要字段的含义、类型、允许范围和可空性。
- 对关键业务状态，定义合法的状态及状态转换条件。
- 对实体之间的关联，明确其业务含义和生命周期。
- 对金额、时间、数量、标识符等重要数据，选择能够准确表达其含义的数据类型。

不要求所有项目都使用复杂的领域模型。简单应用可以采用直接的数据结构和 CRUD 模式；当业务规则、状态约束或数据关系变得复杂时，应适当加强模型表达能力。

### 3.2 在合适的层次保障数据完整性

重要的数据约束应尽可能在能够可靠执行的层次得到保障。

- 在应用层验证业务输入和业务规则。
- 在数据库层使用适当的类型、唯一性约束、外键、检查约束等机制保护数据完整性。
- 对需要原子执行的多步数据变更，采用合适的事务边界。
- 不应只依赖前端校验或单一调用入口保障数据合法性。

并非所有业务规则都适合放入数据库约束，但对于唯一性、引用关系和关键数据范围等能够可靠表达的约束，应评估在持久化层实施保护的价值。

### 3.3 明确数据生命周期

对于重要数据，应根据业务需求明确其创建、使用、保留、归档和删除规则。

- 只收集和保存业务所需的数据。
- 对有明确保留期限的数据，按要求进行归档或清理。
- 对删除操作，明确是否需要软删除、物理删除或保留审计记录。
- 对备份和归档数据，同样实施适当的访问控制和保护措施。

当法律法规、合同或业务政策规定数据保留期限时，应遵循相应要求。不得因为技术便利而无限期保留不再需要的敏感数据。

## 4. 输入验证与数据访问

### 4.1 验证所有不可信输入

来自用户、外部系统、文件、消息队列或其他不可信边界的数据，都应在进入可信业务处理之前接受适当验证。

验证内容应根据场景包括：

- 类型、格式、长度和取值范围。
- 必填字段与字段之间的约束。
- 标识符与资源是否存在。
- 当前业务状态是否允许执行目标操作。
- 调用方是否有权提交或修改相应数据。

前端校验主要用于改善用户体验，不能代替服务端验证。系统应在可信的服务端边界重新验证影响安全性和数据完整性的关键条件。

### 4.2 安全地访问数据库

数据库访问应使用适当的参数化查询或等效安全机制，避免将不可信输入直接拼接进 SQL 或其他查询表达式。

- 优先使用参数化查询和经过验证的数据库访问工具。
- 动态表名、列名、排序字段等无法直接参数化的部分，应使用明确的允许列表或等效约束。
- 不应依赖简单的字符串替换或过滤来防止 SQL 注入。
- 对数据库账号授予满足业务需求的最低权限。

使用 ORM 并不自动意味着不存在注入风险。原生 SQL、动态查询及其他绕过 ORM 的操作同样需要接受安全审查。

### 4.3 限制数据暴露范围

接口和数据访问组件应只返回调用方完成任务所需的信息。

- 避免直接暴露内部数据模型中的全部字段。
- 对敏感字段实施必要的读取和修改权限控制。
- 对列表查询、导出和批量接口设置合理的范围限制。
- 避免通过错误信息、调试输出或元数据泄露不必要的内部信息。

数据传输对象、响应模型或字段白名单可以用于控制数据暴露，但具体方式应服从技术栈和项目结构。

## 5. 身份认证与访问授权

### 5.1 区分认证与授权

身份认证用于确认调用方的身份；访问授权用于判断该身份是否可以执行特定操作或访问特定资源。

两者不可相互替代。成功登录并不意味着用户有权访问所有数据或执行所有业务操作。

系统应使用适合其风险和运行环境的认证机制，并明确不同用户、服务和系统身份的权限范围。

### 5.2 使用统一且可靠的认证机制

身份认证应优先采用成熟、经过验证的框架、协议或身份提供方能力，避免自行实现密码处理、令牌签发和会话安全等容易出错的基础机制。

根据场景，应合理处理：

- 凭证验证与身份生命周期。
- 会话或令牌的有效期、失效与撤销。
- 登录失败、暴力尝试和异常认证行为。
- 密码重置、账号恢复及多因素认证需求。
- 服务间调用所使用的机器身份和凭证。

具体机制应根据应用类型和风险确定。例如，浏览器应用、移动应用和服务间调用的认证方案可能不同，不应机械套用同一实现。

### 5.3 在服务端执行授权检查

授权判断必须在可信的服务端边界得到执行，不能只依赖前端隐藏按钮、禁用菜单或限制页面访问。

对于敏感操作和资源访问，应验证调用方是否具有对应权限。

- 明确不同角色或身份可以执行的操作。
- 对用户拥有的数据，验证资源所有权或相应访问关系。
- 对管理员和高权限操作，实施适当的权限隔离。
- 对服务间调用，验证调用身份及其允许访问的资源范围。
- 当权限信息发生变化时，确保系统按设计及时反映变更。

授权规则可以通过中间件、策略组件、业务操作入口或其他合适方式实现，但必须保证实际访问路径不能绕过必要检查。

### 5.4 在正确的业务边界验证权限

公共认证和授权机制不能取代具体资源及业务操作所需的授权判断。

例如，用户可以登录系统，并不代表其可以读取其他用户的记录；拥有某类资源的读取权限，也不代表其可以删除该资源或修改其所有者。

对于跨模块调用，应明确由哪个可信边界负责验证权限，避免因多层调用或内部接口而遗漏检查。

不应要求每一层重复实现相同的授权逻辑，但应确保关键操作在所有可达路径上都受到有效保护。

## 6. 敏感数据、凭证与密钥管理

### 6.1 识别并减少敏感数据

项目应识别需要重点保护的数据，包括但不限于：

- 密码、访问令牌、API Key 和其他认证凭证。
- 加密密钥、私钥及签名材料。
- 个人信息、财务信息和其他受保护的业务数据。
- 能够用于身份冒用、权限提升或绕过安全控制的信息。

应尽量减少敏感数据的收集、复制和暴露。能够通过引用、短期令牌或其他更低风险方式实现的场景，不应无必要地复制完整敏感数据。

### 6.2 安全管理凭证与密钥

凭证和密钥应通过适当的配置管理或专门的密钥管理机制进行保存和使用。

- 禁止将真实密码、访问令牌、私钥等敏感凭证直接提交到代码仓库。
- 不应将凭证硬编码在源代码、脚本、镜像或公开文档中。
- 不应通过普通日志、异常信息或调试输出暴露凭证。
- 应限制凭证的读取权限和使用范围。
- 应根据风险、有效期和泄露情况执行凭证更新、撤销或轮换。

环境变量可以用于部分运行时配置，但不应将其视为在所有部署环境中都足够安全的通用密钥管理方案。对于高风险或生产环境，应根据实际能力采用更合适的密钥管理设施。

示例配置应使用虚构或明确标记为示例的值，不应包含真实可用的秘密信息。

### 6.3 密码与认证秘密的保护

用户密码不应以明文或可直接还原的形式存储。应使用适合密码存储的专用哈希算法和参数，并根据技术环境及时更新安全配置。

密码哈希与可逆加密用途不同。需要恢复的业务秘密应根据用途使用适当的加密与密钥管理机制，不能以普通密码哈希替代。

认证令牌、重置令牌及其他短期凭证应具有适当的有效期、使用限制和失效机制。具体策略应结合安全风险和业务体验确定。

### 6.4 保护日志、备份与导出数据

敏感数据的保护范围不仅限于主数据库，还应覆盖日志、备份、导出文件、缓存、消息和监控数据。

- 默认不记录密码、完整认证令牌、私钥等秘密。
- 确有业务需要记录敏感信息时，应评估必要性并采用适当的脱敏或访问限制。
- 备份和导出文件应有明确的访问控制和保留期限。
- 测试和开发环境应避免无必要地使用真实敏感数据。
- 对不再需要的敏感数据，应按适用规则进行清理。

脱敏不应仅通过隐藏界面字段实现；应根据数据实际流经的存储、日志和传输路径评估暴露风险。

### 6.5 建立泄露后的处置方式

当发现凭证泄露或敏感数据可能被未授权访问时，应及时采取适当措施。

根据事件情况，措施可以包括：

- 撤销或轮换受影响的凭证。
- 限制相关账号、接口或资源的访问。
- 调查影响范围和可能的访问记录。
- 修复暴露原因，避免同类问题再次发生。
- 根据适用的法律法规和组织要求履行通知、报告或其他处置义务。

仅从当前代码中删除秘密并不能保证历史提交、构建产物、日志和备份中的秘密已经失效。应根据实际暴露范围采取完整处置措施。

## 7. 数据一致性、事务与并发控制

### 7.1 明确关键业务不变量

关键业务不变量是系统必须持续满足的业务条件，例如唯一性、余额不能违反约束、订单状态转换必须合法等。

设计数据变更流程时，应明确：

- 哪些条件必须始终成立。
- 哪些操作可能并发发生。
- 哪些失败情况可能导致部分完成。
- 哪些数据允许短暂不一致，以及这种不一致的可接受范围。

一致性策略应由业务要求和风险决定，而不是单纯由数据库类型或技术偏好决定。

### 7.2 合理划分事务边界

对必须作为一个整体成功或失败的相关数据变更，应使用合适的事务或等效原子机制。

- 事务范围应覆盖必须共同满足的数据约束。
- 避免无必要地扩大事务范围或执行过长事务。
- 对事务失败，应明确回滚、错误返回和后续处理方式。
- 对数据库之外的外部调用，不应假定其会自动参与数据库事务。

事务不能解决所有跨系统一致性问题。对于涉及消息发送、第三方服务或多个独立数据存储的操作，应根据业务风险选择适当的协调、重试、幂等或补偿机制。

### 7.3 处理并发更新

当多个请求可能同时读取或修改同一数据时，应评估并发导致的数据覆盖、重复处理或业务约束失效风险。

根据场景，可以采用：

- 数据库唯一性约束和其他完整性约束。
- 乐观锁、版本号或条件更新。
- 必要范围内的悲观锁。
- 原子更新语句或其他数据库原生并发控制机制。
- 明确的冲突检测与重试策略。

不应仅依赖先查询、再修改的应用层流程来保证并发安全，因为查询与写入之间可能发生竞争。

并发控制方式应与数据访问模式、性能需求和业务约束相匹配。

### 7.4 设计幂等性与重试

对可能因网络故障、超时、重复消息或调用方重试而重复执行的操作，应评估是否需要幂等机制。

尤其是支付、订单创建、状态变更、任务处理等可能产生重复副作用的场景，应明确重复请求的识别方式和预期结果。

- 重试应有明确的触发条件、次数或时间限制。
- 对不具备安全重复执行条件的操作，不应直接无限重试。
- 应区分操作失败、结果未知和操作已成功等不同情况。
- 对无法原子完成的多步操作，应根据业务影响评估补偿和人工处理机制。

幂等机制并非要求每个函数都引入唯一请求标识，而是要求对具有重复执行风险的重要操作进行有针对性的保护。

### 7.5 谨慎处理跨系统一致性

跨服务或跨存储的数据变更，可能无法通过单一数据库事务保证原子性。

项目应根据实际需求选择同步调用、可靠消息、最终一致性、补偿流程或其他适合的机制，并明确：

- 哪些状态可能暂时不一致。
- 如何检测和恢复失败。
- 如何避免重复处理和丢失关键事件。
- 如何处理部分成功和无法自动恢复的情况。

不应为所有业务引入复杂的分布式事务机制，也不应在关键业务要求明确的情况下忽略跨系统失败风险。

## 8. 加密、网络与外部系统交互

### 8.1 根据风险采用适当的加密措施

对于敏感数据，应根据其敏感程度、传输路径和存储环境评估加密需求。

- 在不可信网络中传输敏感信息时，应使用适当的安全传输机制。
- 对需要保护的静态数据，应根据风险、平台能力和密钥管理条件评估加密措施。
- 加密算法和协议应优先采用成熟、经过验证的实现。
- 密钥与被保护的数据应避免采用会导致同一风险点失效的管理方式。

加密不能替代访问控制、密钥管理和安全配置。采用加密后，仍需评估密钥泄露、授权绕过和数据使用过程中的暴露风险。

### 8.2 安全访问外部系统

访问第三方 API、Webhook、文件、消息和其他外部资源时，应明确输入可信度、身份验证方式和失败处理。

- 对外部返回的数据进行适当验证。
- 对访问目标、协议和资源范围实施必要限制。
- 对外部调用设置合理的超时与错误处理。
- 避免将外部系统返回的内容直接作为可信业务指令或安全决策依据。
- 对涉及敏感数据的外部传输，明确必要性和授权依据。

当系统允许用户提供 URL、文件路径或其他可能影响资源访问目标的输入时，应评估服务器端请求伪造、路径穿越及类似风险，并根据场景采取限制措施。

### 8.3 控制错误信息与安全日志

错误处理应在提供足够诊断信息与避免泄露内部细节之间取得平衡。

- 面向用户的错误信息不应暴露秘密、内部路径、数据库结构或不必要的系统细节。
- 服务端日志应保留排查问题所需的上下文，同时避免记录敏感数据。
- 对认证失败、权限拒绝和重要安全事件，应根据风险记录必要信息。
- 日志访问、保留和删除应遵循相应的安全与运维要求。

日志应有助于识别和调查问题，但不应成为新的敏感数据泄露渠道。

## 9. 备份、恢复与数据删除

### 9.1 根据业务影响确定恢复要求

对重要数据，应明确备份与恢复需求，并根据业务影响确定适当的恢复目标。

需要考虑：

- 数据丢失的可接受范围。
- 服务中断的可接受时长。
- 备份频率与保留策略。
- 备份数据的访问控制和保护措施。
- 恢复过程的可执行性和验证方式。

备份任务执行成功并不意味着数据一定可以恢复。对于重要系统，应定期验证备份可用性和恢复流程。

### 9.2 谨慎执行删除与不可逆操作

删除、覆盖和批量变更等不可逆或高影响操作，应具有适当的保护措施。

- 明确操作范围和影响对象。
- 对高风险操作采用适当的权限限制和确认机制。
- 根据业务需要保留审计记录或恢复能力。
- 对无法恢复的数据，应明确其风险和处理要求。

软删除、归档、物理删除和保留审计记录各有适用场景，应根据业务、隐私和合规要求选择，不应将任何一种方式作为所有项目的统一答案。

## 10. 安全规范的约束与例外

### 10.1 必须遵守的安全底线

以下要求属于通用安全底线，不应在缺乏充分依据和风险控制的情况下绕过：

- 不得将密码、有效凭证、私钥等秘密以不安全方式暴露或提交到公开代码仓库。
- 不得仅依赖前端控制来保护敏感操作或资源。
- 不得将不可信输入未经适当验证和安全处理，直接用于可能导致注入、越权访问或其他危险后果的操作。
- 不得忽视重要数据变更的完整性约束和已知并发风险。
- 不得无故授予超出业务需要的访问权限。
- 不得在已发现严重数据泄露或凭证泄露风险时，明知风险存在却不采取合理处置措施。

上述底线约束的是必须达到的安全结果，并不意味着所有项目都必须使用相同的产品、协议或基础设施。

### 10.2 按风险选择实施措施

具体控制措施应结合以下因素确定：

- 数据的敏感程度与业务价值。
- 系统是否对公网开放，以及信任边界的复杂程度。
- 未授权访问或数据损坏可能造成的影响。
- 业务可用性、恢复要求和维护周期。
- 团队能力、技术栈与运行环境。
- 适用的法律法规、合同和组织政策。

风险较高的系统应采用更严格的控制措施。对于风险较低的系统，可以采用更轻量的实现，但仍须满足适用的安全底线。

### 10.3 管理合理例外

当项目存在明确的技术限制或业务原因，无法直接采用某项默认实践时，应评估替代方案是否能够达到相当的安全与完整性目标。

对涉及重要数据、权限或安全风险的例外，应记录：

- 例外的原因和适用范围。
- 主要风险及可能影响。
- 替代控制措施。
- 必要的后续改进或重新评估条件。

例外不应被用来规避明确的法律法规、合同义务或不可接受的安全风险。对于必须满足的外部合规要求，应遵循相应的正式要求。

例外处理方式应与风险相匹配；具体记录和确认要求遵循《工程原则与架构决策》及 `CONTRIBUTING.md` 中的统一约定。

## 11. 安全与数据质量检查清单

在设计评审、代码评审、上线检查或风险评估中，可以根据变更范围选用以下检查项。

### 数据管理

- [ ] 重要数据是否有明确的业务归属和访问边界？
- [ ] 关键字段、状态和数据关系是否具有合理的完整性约束？
- [ ] 不可信输入是否在可信服务端边界接受验证？
- [ ] 数据查询和修改是否受到适当权限控制？
- [ ] 数据收集、保留、导出和删除是否符合实际业务要求？

### 身份与访问授权

- [ ] 身份认证机制是否适合应用类型和风险？
- [ ] 敏感操作和资源访问是否在服务端执行授权检查？
- [ ] 是否避免仅依赖前端限制访问？
- [ ] 服务账号与第三方凭证是否遵循最小权限原则？
- [ ] 重要权限变更是否能够及时生效？

### 敏感信息保护

- [ ] 代码、配置、日志和文档中是否存在真实秘密信息？
- [ ] 密码、令牌和密钥是否采用适当的保护机制？
- [ ] 日志、备份、缓存和导出数据是否受到保护？
- [ ] 是否有合理的凭证泄露处置方式？
- [ ] 敏感数据的保留期限和清理要求是否明确？

### 一致性与可靠性

- [ ] 关键业务不变量是否明确？
- [ ] 事务边界是否覆盖必须原子完成的数据变更？
- [ ] 是否评估并发更新和重复请求风险？
- [ ] 重试是否安全、有限且有明确条件？
- [ ] 跨系统部分失败是否有合理的检测、恢复或补偿方案？
- [ ] 重要数据是否具有符合业务要求的备份与恢复能力？

检查清单用于辅助风险识别，不要求每次普通代码修改都执行完整审计。检查深度应与数据敏感程度、变更影响和系统风险相匹配。

## 12. 与其他规范的关系

本文规定数据管理、身份认证、访问授权、敏感信息保护、数据一致性和安全风险控制的通用要求。

- **工程原则与架构决策**：定义工程质量底线、设计权衡、架构选择和重要决策的处理方式。
- **代码组织与职责边界**：细化模块、Action、Service、Repository 等组件的职责与依赖边界。
- **测试与质量保证**：细化安全验证、数据完整性测试、测试分层和自动化质量检查。
- **Git 与协作流程**：细化提交、评审、分支和协作过程中的安全要求。
- **文档与项目状态管理**：细化数据字典、配置说明、风险记录和维护文档的管理。
- **AI 辅助开发**：细化 AI 工具接触敏感数据、使用凭证和生成安全相关代码时的要求。
- **交付与持续改进**：细化部署配置、运行监控、备份恢复和安全事件后的改进机制。

本文不替代具体技术栈的安全指南、适用的法律法规或项目必须遵守的合规要求。项目应在满足这些约束的基础上，采用与自身风险相匹配的实现方式。
