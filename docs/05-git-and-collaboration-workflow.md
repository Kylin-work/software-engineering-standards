# Git 与协作流程

- **状态**：Draft
- **适用范围**：通用软件工程项目
- **主题定位**：规范版本控制、分支管理、提交信息、代码评审、变更合并及历史追溯的基本要求

## 1. 目的与适用范围

本文建立通用的 Git 使用与协作流程准则，帮助项目保持清晰、可追溯的变更历史，降低多人协作中的冲突和误操作风险，并在交付效率与质量控制之间取得合理平衡。

本文适用于个人维护、多人协作、开源项目和持续交付等不同工作模式。

本文不强制所有项目采用统一的分支模型、Commit Message 格式、合并策略或 Pull Request 流程。项目应根据团队规模、发布方式、风险等级和工具能力选择适当的实施方式。

本文遵循以下原则：

- 变更应具有明确目的，并能够通过版本历史追溯。
- 分支策略应尽量轻量，避免不必要的长期分支和流程负担。
- 提交历史应准确表达变更意图，便于后续理解和排查问题。
- 代码评审和自动化检查应与变更风险相匹配。
- 重要分支应保持可用，合并方式应服务于项目的维护和追溯需求。
- 对共享历史和破坏性操作应谨慎处理。
- 紧急修复可以简化流程，但不能忽视必要的安全与质量控制。

## 2. 基本原则

### 2.1 变更应清晰且可追溯

Git 历史应帮助维护者回答以下问题：

- 为什么进行这次变更？
- 变更解决了什么问题或增加了什么能力？
- 主要影响哪些模块、功能或配置？
- 是否存在重要的设计取舍、风险或后续工作？

提交信息、Pull Request 描述及相关文档应共同提供必要上下文。

不要求每次修改都编写冗长说明，但不应使用无法表达实际意图的信息掩盖重要变更。

### 2.2 流程服务于协作，而非增加形式负担

项目应采用与其规模和风险相匹配的协作流程。

个人维护的小型项目可以采用直接提交、轻量检查等方式；多人协作项目通常需要明确分支、评审和合并规则；对安全、数据完整性或交付风险较高的变更，则应加强控制。

不应为了形式上的流程完整而增加没有实际价值的审批、分支或文档要求，也不应以追求效率为由省略必要的风险控制。

### 2.3 共享历史应谨慎维护

已经被他人基于其开展工作的提交历史，应视为共享历史。

对共享历史进行重写、强制推送或其他可能改变他人工作基础的操作前，应评估影响并与相关协作者协调。

对于尚未共享的本地提交，可以根据需要整理提交历史，但应确保操作结果清晰且不会丢失重要工作。

## 3. 分支策略

### 3.1 默认采用轻量分支策略

项目应优先选择能够满足协作与发布需求的最简单分支模型。

推荐做法：

- 小型个人项目可以直接在主分支上完成低风险修改。
- 多人协作项目通常使用短生命周期功能分支，并通过 Pull Request 或其他评审方式合并。
- 需要维护多个发布版本的项目，可以根据实际需要设置发布分支或维护分支。
- 不应仅因为某种分支模型较为流行，就在没有实际需求时引入复杂的长期分支体系。

分支模型应服务于实际工作流程，而不是成为必须遵守的形式。

### 3.2 保持分支职责明确

项目使用多个分支时，应明确其用途和生命周期。

例如：

- 主分支用于保存项目当前认可的集成状态。
- 功能分支用于开发某项功能或完成一组相关变更。
- 修复分支用于隔离需要单独验证的缺陷修复。
- 发布或维护分支用于有明确需求的版本维护工作。

分支名称应尽量简洁、可理解，并遵循项目约定。

功能分支完成后，应及时合并或关闭，避免长期积累与主分支之间的差异。

### 3.3 控制分支生命周期

短生命周期分支有助于缩小变更范围、减少合并冲突并及时获得反馈。

应尽量避免：

- 功能分支长期不与主分支同步。
- 一个分支混合大量无关功能和重构。
- 多个分支长期重复实现相同变更。
- 在无法说明用途的情况下保留过多长期分支。

对于确实需要长期维护的分支，应明确其维护目的、同步方式和最终处理计划。

### 3.4 分支策略应与发布方式匹配

持续交付、定期发布和多版本维护可能需要不同的分支策略。

项目可以根据需要采用主干开发、功能分支、发布分支或其他合适的模式，但应确保：

- 分支职责清楚。
- 变更合并路径可理解。
- 发布版本能够追溯到对应的代码状态。
- 修复能够在必要的维护版本之间得到同步。
- 分支之间不会形成难以管理的长期分歧。

不要求所有项目统一采用 Git Flow 或其他固定工作流。

## 4. Commit 与提交信息

### 4.1 一个提交应表达清晰的变更目的

Commit 应尽量围绕一个明确的目的组织，便于理解、评审、回滚和问题定位。

相关修改可以放在同一提交中；彼此无关且能够独立理解的变更，通常应考虑拆分。

不要求每个提交都只修改一个文件或只包含一行逻辑。拆分的目标是提高变更的可理解性，而不是机械追求提交数量。

### 4.2 提交信息应简洁、准确

Commit Message 应让维护者能够快速理解本次提交的主要目的。

推荐做法：

- 标题简明说明变更内容或解决的问题。
- 使用清晰、具体的描述，避免没有实际信息的泛化标题。
- 标题与实际变更保持一致。
- 对涉及多项重要内容的提交，在详细描述中列出主要变更。
- 对重要的设计取舍、兼容性影响或已知限制，补充必要说明。

例如：

```text
新增用户权限校验

- 增加关键操作的访问授权检查
- 补充未授权访问的处理逻辑
- 增加相关测试用例
```

项目可以统一使用中文或英文提交信息，也可以采用 Conventional Commits 等固定格式。除非项目需要依赖特定格式进行自动化处理，否则不要求所有项目强制采用同一种格式。

### 4.3 避免难以追溯的提交

应避免长期使用以下类型的提交信息：

- `update`
- `fix`
- `change`
- `修改代码`
- `临时提交`

这些标题并非在所有情况下都不可使用，但如果无法说明具体目的，应补充更明确的信息。

对于需要进一步完善的临时提交，应在合并前根据项目约定整理提交历史；已经共享的提交则应谨慎处理，不应为了追求标题整齐而随意重写历史。

### 4.4 提交应保持必要的完整性

提交应尽可能处于可理解、可检查的状态。

对于包含代码、测试、配置或文档的变更，应根据实际情况一并提交相关内容，避免出现代码已经修改但必要测试、配置或说明遗漏的情况。

不要求每个提交都必须能够独立发布，但应避免提交明显不完整、无法理解或会破坏协作基础的变更。

### 4.5 注意提交内容与敏感信息

提交前应检查变更内容，避免将不应进入版本控制的信息写入仓库。

尤其应注意：

- 密码、访问令牌和私钥。
- 生产环境凭证与敏感配置。
- 未经授权的个人信息或业务数据。
- 临时文件、构建产物及其他不应长期维护的文件。

敏感信息一旦进入 Git 历史，即使后续提交删除，也不代表其已经从历史记录中消失。发生泄露时，应按照安全事件处理要求采取措施，必要时立即撤销或轮换相关凭证。

## 5. Pull Request 与代码评审

### 5.1 团队协作默认采用可追溯的评审流程

多人协作项目通常应通过 Pull Request（PR）、Merge Request（MR）或等效机制完成变更评审。

评审流程应帮助协作者：

- 理解变更目的和影响范围。
- 发现业务逻辑、设计、安全和维护性问题。
- 检查必要的测试与质量验证。
- 在合并前明确尚未解决的风险。
- 保留重要讨论和决策记录。

个人维护项目可以采用更轻量的方式，例如直接提交主分支；如果项目已有明确的分支保护、评审或合规要求，则应遵循相应约定。

### 5.2 评审深度应与风险匹配

评审不应只由代码行数决定，也应考虑变更的重要性和潜在影响。

通常需要更充分评审的变更包括：

- 认证、授权、敏感数据处理及安全控制。
- 数据库结构、数据迁移和关键事务逻辑。
- 公共接口、共享组件和核心业务规则。
- 大范围重构、关键依赖升级或架构调整。
- 可能影响服务可用性、数据完整性或回滚能力的修改。

小范围、低风险的修改可以采用简洁的评审方式。高风险变更应提供充分的背景、验证证据和风险说明。

### 5.3 提供清晰的变更说明

PR/MR 描述应根据变更复杂度说明必要信息。

对于较重要的变更，建议包含：

- **变更目的**：解决的问题或实现的目标。
- **主要内容**：关键修改及其影响范围。
- **验证情况**：执行了哪些测试或检查。
- **风险与限制**：已知问题、兼容性影响或未覆盖场景。
- **相关依据**：关联的 Issue、设计决策或其他背景材料。

简单修改不需要强制填写冗长模板，但评审者应能够获得理解变更所需的信息。

### 5.4 评审应关注实质问题

评审重点应包括：

- 功能和业务逻辑是否正确。
- 职责边界、依赖关系和实现复杂度是否合理。
- 是否存在安全、数据完整性、并发或异常处理问题。
- 测试是否覆盖重要行为和风险。
- 是否引入不必要的兼容性或维护负担。

格式、命名和基础静态检查应尽可能交由自动化工具处理，以便人工评审集中关注更有价值的问题。

### 5.5 明确评审意见的处理结果

评审意见应尽量具体，说明问题、影响或建议的调整方向。

对于重要问题，应在合并前完成修复或明确处理方案。

对于存在合理分歧的设计问题，应根据业务目标、技术约束和长期维护成本进行讨论，不应将个人偏好自动视为强制规范。

如果决定暂不处理某项非阻断问题，应在必要时记录理由和后续安排。

## 6. 合并策略与主分支保护

### 6.1 保持主分支处于可维护状态

主分支应尽量保持为可理解、可验证且能够继续开展工作的状态。

项目可以通过测试、静态检查、代码评审、分支保护或其他适当机制降低主分支被破坏的风险。

保护措施应根据项目特点设置，不要求所有项目启用完全相同的 Git 平台功能。

对于重要项目，应明确哪些检查必须通过、哪些变更需要评审，以及谁有权执行高风险操作。

### 6.2 根据项目需求选择合并方式

常见的合并方式包括：

- **Merge Commit**：保留分支合并关系，适合需要明确记录集成过程的场景。
- **Squash Merge**：将分支中的多个提交合并为一个提交，适合希望主分支历史更简洁的场景。
- **Rebase**：通过调整提交基线整理历史，适合有明确历史管理约定的场景。

不同方式各有取舍。项目应根据追溯需求、提交组织方式、发布流程和团队习惯选择合适方案。

不应强制所有项目统一采用一种合并策略，也不应仅以历史是否整齐作为判断标准。

### 6.3 合并前完成必要验证

合并前应确认变更满足项目约定的基本条件。

根据风险和流程，可以包括：

- 相关测试和必要的自动化检查已通过。
- 重要评审意见已处理。
- 不存在未解决的关键冲突。
- 变更范围和提交内容符合预期。
- 需要的文档、配置和迁移说明已经补充。

对于无法完成的验证，应明确原因和剩余风险。不能仅因为合并流程方便，就默认跳过关键的安全、数据完整性或可靠性检查。

### 6.4 控制合并权限与破坏性操作

对于重要主分支，应限制可能造成不可恢复影响的操作，例如未经协调的强制推送、删除关键分支或绕过必要质量门禁。

项目可以根据团队规模和风险采用不同的权限控制方式。

个人维护项目也应注意保护唯一工作副本、重要版本标签和其他难以恢复的历史信息。

## 7. 冲突解决与历史管理

### 7.1 尽早处理合并冲突

合并冲突是协作过程中正常出现的情况。发生冲突时，应根据代码上下文和业务含义判断正确结果，而不是机械选择某一侧的内容。

处理冲突时应：

- 理解冲突双方的变更目的。
- 检查相关逻辑是否存在行为差异。
- 保留双方仍然有效的修改。
- 删除已经失效或重复的实现。
- 对关键逻辑执行适当测试。
- 确认解决冲突没有引入新的回归问题。

对于复杂冲突，应与相关变更的作者沟通，避免在不了解业务含义的情况下直接覆盖修改。

### 7.2 区分本地历史与共享历史

对于尚未共享的本地提交，可以根据需要使用交互式 Rebase、Squash 或其他方式整理提交。

对于已经推送且可能被他人使用的共享历史，应优先保持稳定。

确需重写共享历史时，应：

- 明确操作目的和影响范围。
- 提前与相关协作者协调。
- 确认其他人的工作不会因此丢失。
- 在必要时提供恢复或同步指导。

不应在共享分支上未经协调地执行可能导致他人工作混乱的历史重写。

### 7.3 合理使用 Revert 与 Reset

回退变更时，应根据变更是否已经共享及回退目标选择适当方式。

- **Revert**：通过新增反向提交撤销既有变更，通常更适合已经共享的提交。
- **Reset**：调整当前分支的提交位置，通常更适合尚未共享的本地提交整理。

上述原则并非绝对限制，但应充分考虑操作是否会改写共享历史、影响其他协作者或导致未保存工作丢失。

对于已经进入共享历史的错误变更，通常优先考虑使用可追溯的 Revert，而不是直接重写历史。

### 7.4 处理误提交与敏感信息泄露

发现误提交时，应先判断影响范围和内容性质。

如果涉及密码、令牌、私钥或其他敏感信息，应立即按照安全事件处理要求采取措施，包括必要的凭证撤销或轮换。

仅删除文件或新增删除提交，并不能保证敏感内容从 Git 历史、远端副本、缓存或其他协作者的本地副本中消失。

如果需要清理历史，应制定明确的处理方案，并协调相关协作者。历史清理不能替代对已泄露凭证的处置。

## 8. 标签、版本与发布追溯

### 8.1 重要版本应具有明确的追溯依据

需要发布版本或维护多个版本的项目，应根据实际需求使用 Git Tag、发布记录或其他方式标识重要状态。

版本信息应能够关联到对应的代码状态及必要的发布说明。

不要求所有小型项目都建立完整的版本发布体系，但对于需要重复构建、维护历史版本或定位线上问题的项目，应保留足够的追溯信息。

### 8.2 发布标签应保持可信

用于正式发布或其他重要用途的标签，应具有明确含义，并遵循项目约定。

不应在未说明的情况下随意移动、重用或删除已经被外部流程依赖的重要标签。

如果确实需要修正错误的版本标记，应明确说明原因，并确保相关协作者、构建流程和发布记录得到同步。

### 8.3 版本管理方式应与项目需求匹配

项目可以采用语义化版本、日期版本或其他合理方式管理版本。

版本命名应有助于理解版本顺序、兼容性或发布范围。只有在项目确实需要自动化版本管理、依赖兼容性表达等能力时，才需要引入更严格的版本约定。

## 9. 紧急修复与流程例外

### 9.1 允许合理简化流程

生产故障、安全事件或其他紧急情况可能需要缩短正常协作流程。

在确有必要时，可以采用更轻量的评审、验证或合并流程，但应根据风险保留必要的安全和正确性检查。

流程简化不代表可以忽视：

- 对关键数据和系统状态的保护。
- 重要权限和安全控制。
- 变更影响及潜在副作用。
- 必要的恢复或回滚方案。

### 9.2 紧急变更应补充必要记录

紧急修复完成后，应根据影响范围补充必要的变更说明、验证结果和风险记录。

对于重要事故，还应评估是否需要补充回归测试、改进自动化检查或调整正常协作流程。

不要求每次紧急修改都编写正式复盘报告，但应确保重大变更仍然能够被理解、追溯和维护。

### 9.3 例外应有明确边界

对于确实不适用默认流程的情况，可以采用合理例外。

例外应与实际风险相匹配，并在必要时说明：

- 为什么无法遵循默认流程。
- 采用了哪些替代措施。
- 剩余风险是什么。
- 是否需要后续补充验证或恢复常规流程。

不应让临时例外在没有评估的情况下长期成为规避必要质量控制的固定做法。

## 10. Git 与协作检查清单

以下清单可用于提交变更、代码评审、合并和发布准备。应根据项目流程与风险选择适用项。

### 变更与提交

- [ ] 变更目的清晰，相关修改组织合理。
- [ ] Commit Message 能准确表达主要变更。
- [ ] 重要变更已补充必要的详细描述。
- [ ] 没有意外提交敏感信息、临时文件或无关产物。
- [ ] 相关测试、配置和文档已根据需要一并更新。

### 分支与评审

- [ ] 分支用途清晰，生命周期符合项目约定。
- [ ] 变更范围与本次任务目标一致。
- [ ] 重要变更已进行适当的代码评审。
- [ ] 高风险变更已提供必要的验证证据和风险说明。
- [ ] 重要评审意见已经处理或明确安排后续工作。

### 合并与历史

- [ ] 合并前已完成必要的测试和质量检查。
- [ ] 关键冲突已根据实际业务逻辑解决。
- [ ] 主分支及重要分支未受到不必要的破坏性操作影响。
- [ ] 对共享历史的重写或强制推送已进行必要协调。
- [ ] 回滚方式与提交是否共享、操作影响和恢复目标相匹配。

### 发布与例外

- [ ] 重要版本或发布状态具有必要的追溯依据。
- [ ] 需要时已建立清晰的版本标签或发布记录。
- [ ] 紧急变更保留了必要的安全和正确性控制。
- [ ] 重要例外及其剩余风险已得到适当记录。
- [ ] 重大问题已评估是否需要回归测试或流程改进。

清单用于辅助判断，不要求每次普通提交都执行全部项目。检查深度应与变更影响、协作规模和失败风险相匹配。

## 11. 与其他规范的关系

本文规定 Git 使用、分支策略、提交信息、代码评审、合并和历史管理方面的通用要求。

- **工程原则与架构决策**：定义工程质量底线、设计权衡和架构决策方式。
- **代码组织与职责边界**：明确代码组织、模块职责和依赖边界。
- **数据与安全**：定义敏感信息保护、访问控制及数据安全要求。
- **测试与质量保证**：规范测试分层、质量检查、回归测试和持续集成。
- **文档与项目状态管理**：规范项目说明、决策记录、维护状态和变更相关文档。
- **AI 辅助开发**：规范 AI 生成变更的检查、验证和责任归属。
- **交付与持续改进**：规范发布追溯、部署流程、回滚准备和改进机制。

本文不要求所有项目使用统一的 Git 平台、分支模型、Commit Message 格式或合并策略。项目应在满足必要的安全、质量和追溯要求的前提下，选择适合自身工作方式的协作流程。
